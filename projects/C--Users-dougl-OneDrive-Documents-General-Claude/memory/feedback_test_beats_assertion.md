When a claim is empirically checkable in ~2 minutes (does this syntax render? does this command work? does this file exist?), RUN THE TEST before asserting it, before searching, and before arguing. Evidence hierarchy: a working example > the user's direct experience > a fresh test I run > web search > my training memory. If a search result contradicts the user's lived experience or a runnable test, that is a signal to TEST — not to double down on the search.

**Why:** The checkbox-in-Obsidian-table saga (2026-05-30). Doug said "I know it can"; I trusted a single defeatist web-search hit over his direct experience and over a trivially-available screenshot test, then asserted "needs a plugin" as fact. The working syntax (`<input type="checkbox">`) was provable on minute one with one test note. I also kept thrashing after two options (D and F) had already rendered correctly. Doug's correction: "web research can come first as long as you don't suck at it" — research order is not the problem; research quality + empirical verification is.

**How to apply:** Before stating any empirically-checkable claim, ask "can I test this cheaply right now?" If yes, test first — the test is authoritative. Treat the user's "I know X works" as a strong prior that outranks a generic search result. When something already works, anchor on it (ask _why_ it works and what transfers) instead of re-testing or chasing alternatives. A lone forum claim is "single source," not proof of impossibility — honor the ≥2-source rule from [[feedback_verify_before_asserting]]. Separate "assumed" from "verified": never assert an unchecked empirical claim as fact — verify it or hedge it explicitly.

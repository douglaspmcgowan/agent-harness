# /make-playbook

## When to invoke

- User explicitly asks: "make a playbook", "active playbook skill", "capture this workflow"
- End of any session that involved:
  - First successful deploy of a new site or tool type
  - A debugging arc with ≥3 steps before resolution
  - A new tool or API integrated for the first time
  - A multi-step process that will clearly repeat (e.g., "every time I spin up a site...")

Do NOT invoke for one-off tasks that won't repeat, or tasks already fully covered by an existing playbook.

---

## Phase 1 — Classify and check skill-candidacy

Determine the playbook type before writing anything:

- **General** → goes in `Claude Research Folder/playbooks/` (any project can use it)
- **Project-specific** → goes in that project's folder as `PLAYBOOK.md` or `playbooks/<name>.md`
- **Domain** → goes in `Claude Research Folder/playbooks/<domain>/` (e.g., fellowship/, sites/)

Ask the user to confirm the classification if unclear.

**General playbooks always go in `playbooks/` — never at the repo root.** If the user already
has a root-level `*playbook*.md` that matches, note the duplicate and offer to clean it up
after saving (don't delete it automatically — ask first).

**Skill candidacy check:** after classifying, ask: does this playbook describe an _action_
a Claude session would take (build X, review Y, run Z) rather than just document what happened?
If yes, it's a candidate for a `/skill` too — not a replacement for the playbook, but a machine-
readable wrapper that invokes it. Note this at the end and offer to create one with the skill-creator.
Examples of action-playbooks that warranted skills: `fellowship-review`, `build-tracker`, `deep-search`.

---

## Phase 2 — Extract context

Gather the raw material. Run these in parallel:

1. **Git log** — `git log --since="8 hours ago" --oneline --all` in the relevant repo(s).
   If no git, check file mtimes with Glob.
2. **Conversation context** — summarize the key steps, errors hit, and decisions made
   from this session (use what's in context, don't re-read files you haven't read).
3. **Existing playbooks** — Glob `Claude Research Folder/playbooks/*.md` and skim
   their H2 headings. If the pattern is already covered, extend the existing file
   instead of creating a new one.
4. **Root-level duplicate check** — Glob `Claude Research Folder/*playbook*.md` and
   `Claude Research Folder/*-playbook.md`. Note any that overlap with the new one.

---

## Phase 3 — Draft the playbook

Write the playbook using this template:

```markdown
# Playbook: [Short imperative name — e.g., "Deploy a Static Vercel Site"]

> One-sentence description of what this covers and when to use it.

**Category:** [General / Project-specific / Domain]
**Time estimate:** [e.g., "~45 min first time, ~15 min with this playbook"]
**Last updated:** [YYYY-MM-DD]

---

## When to use this playbook

[2–4 bullet conditions that mean "yes, follow this playbook now"]

## Prerequisites

[Checklist of tools, auth, config that must be in place before starting]

## Process

### Step 1 — [Name]

[What to do, exact commands or file paths where relevant]

### Step 2 — [Name]

...

## Common errors and fixes

| Error                      | Cause        | Fix         |
| -------------------------- | ------------ | ----------- |
| [error message or symptom] | [root cause] | [exact fix] |

## Decisions log

[Key choices made and WHY — the things you'd forget and re-derive next time]

## Reuse checklist

- [ ] [Thing to verify before starting if reusing this pattern]
- [ ] ...

---

_Generated by /make-playbook on [date]. Edit freely._
```

Quality bar:

- The "Common errors" section is the highest-value part. Every error that took >5 min to fix goes here.
- "Decisions log" should have the WHY, not just the what. Future-you will re-derive the what from the code.
- Keep the process steps short. If a step needs a paragraph, it needs its own sub-section.

---

## Phase 4 — Save and register

1. Determine the save path based on Phase 1 classification. **General playbooks always go in
   `playbooks/` — never at the repo root.** If a root-level copy already exists, flag it:
   "There's also `root/[name].md` — want me to delete the root copy now that `playbooks/` has
   the canonical version?" Do not delete it without confirmation.
2. Write the file.
3. Update `Claude Research Folder/playbooks/INDEX.md`:
   - If it doesn't exist yet, create it with the standard header (see existing file for format).
   - Determine the next unused P# by reading the current table.
   - Append a row under the correct section (General / Project / Domain / Fellowship):
     ```
     | P# | [filename](filename) | [one-line description] | [today's date] |
     ```
4. If the playbook is project-specific, also note it in that project's `STATUS.md` or `README.md`.
5. If Phase 1 flagged skill-candidacy, offer: "This playbook describes a repeatable action —
   want me to create a `/[name]` skill that wraps it? Use `anthropic-skills:skill-creator`."
6. Confirm to the user: "Saved to `[path]`. INDEX updated at row P#."

---

## Quality gate before saving

Do not save if:

- The playbook duplicates an existing one entirely (extend instead)
- It has fewer than 3 process steps and no error table (not enough to be useful)
- The task was a one-off with no clear repeat trigger

If any gate fails, tell the user why and ask if they still want it saved.
